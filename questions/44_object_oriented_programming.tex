\section{Базовые концепции объектно-ориентированного программирования}

Объектно-ориентированное программирование (ООП) --- парадигма программирования, в которой программа представляется как совокупность взаимодействующих объектов. Каждый объект обладает состоянием, поведением и идентичностью.

Основными понятиями ООП являются классы и объекты, инкапсуляция, наследование, полиморфизм и абстракция. На практике важную роль также играют композиция объектов, интерфейсы и принципы проектирования, позволяющие строить расширяемые и сопровождаемые программные системы.

\subsection{Объекты и классы}

\textbf{Объект} --- сущность программы, обладающая:
\begin{itemize}
	\item \textbf{состоянием} --- совокупностью хранимых данных;
	\item \textbf{поведением} --- набором операций, которые объект способен выполнять;
	\item \textbf{идентичностью} --- возможностью отличить данный объект от других, даже если их состояния совпадают.
\end{itemize}

Например, объект, представляющий матрицу, может хранить её размеры и элементы, а также предоставлять операции сложения, умножения, вычисления нормы и т.д.

\textbf{Класс} --- описание множества объектов с общей структурой и поведением. Класс определяет:
\begin{itemize}
	\item набор данных или полей;
	\item набор методов;
	\item правила создания объектов и, в зависимости от языка, управления их жизненным циклом;
	\item ограничения доступа к отдельным элементам объекта.
\end{itemize}

Объект называют \textbf{экземпляром класса}.

Условно класс можно представить следующим образом:
\begin{verbatim}
	class Vector {
		data
		coordinates
		
		methods
		norm()
		add(Vector other)
	}
\end{verbatim}

Конкретные объекты
\begin{verbatim}
	v1 = Vector(...)
	v2 = Vector(...)
\end{verbatim}

являются различными экземплярами одного класса \texttt{Vector}.

Следует различать \textbf{класс} и \textbf{тип}. Во многих объектно-ориентированных языках класс задаёт новый тип, но в общем случае эти понятия не тождественны. Например, интерфейс также может задавать тип, не задавая конкретного способа хранения состояния объекта.

\subsection{Инкапсуляция}

\textbf{Инкапсуляция} --- объединение данных и операций над ними внутри некоторой программной сущности с контролем доступа к её внутреннему состоянию.

Основная идея состоит в том, что пользователь объекта взаимодействует не с его внутренним представлением, а с некоторым публичным интерфейсом.

Например, если класс описывает банковский счёт, непосредственное произвольное изменение величины баланса нежелательно:
\begin{verbatim}
	account.balance = -1000000
\end{verbatim}

Вместо этого состояние должно изменяться посредством допустимых операций:
\begin{verbatim}
	account.deposit(amount)
	account.withdraw(amount)
\end{verbatim}

Метод \texttt{withdraw} может проверить достаточность средств и тем самым поддерживать корректность состояния объекта.

Таким образом, инкапсуляция позволяет поддерживать \textbf{инварианты объекта} --- свойства, которые должны оставаться истинными при всех допустимых операциях.

Во многих языках для управления доступом используются модификаторы:
\begin{itemize}
	\item \texttt{public} --- элемент доступен пользователю класса;
	\item \texttt{private} --- элемент доступен только внутри самого класса;
	\item \texttt{protected} --- элемент имеет ограниченную видимость, обычно доступен внутри класса и его наследников; точные правила зависят от языка.
\end{itemize}

Инкапсуляция уменьшает зависимость внешнего кода от внутреннего устройства класса. Например, внутреннее представление контейнера можно заменить с массива на связный список без изменения пользовательского кода, если публичный интерфейс остаётся тем же.

Следует отличать инкапсуляцию от простого \textbf{сокрытия данных}. Сокрытие данных ограничивает прямой доступ к внутреннему состоянию объекта, например с помощью модификатора \texttt{private}. Инкапсуляция является более широким понятием: объект объединяет состояние и операции над ним, предоставляет контролируемый публичный интерфейс и самостоятельно обеспечивает корректность своего состояния.

\subsection{Наследование}

\textbf{Наследование} --- механизм создания нового класса на основе существующего, при котором новый класс получает часть свойств и поведения базового класса и может расширять или изменять их.

Исходный класс называют \textbf{базовым} или \textbf{родительским}, а новый --- \textbf{производным} или \textbf{дочерним}.

Например:
\begin{verbatim}
	class Shape {
		area()
	}
	
	class Circle extends Shape {
		radius
		area()
	}
	
	class Rectangle extends Shape {
		width
		height
		area()
	}
\end{verbatim}

Классы \texttt{Circle} и \texttt{Rectangle} имеют общее свойство: оба являются геометрическими фигурами и поддерживают операцию вычисления площади.

Наследование решает две основные задачи:
\begin{enumerate}
	\item повторное использование некоторой реализации;
	\item построение иерархии типов.
\end{enumerate}

Особенно важно различать эти задачи: само по себе желание переиспользовать код не является достаточным основанием для наследования. При использовании наследования для построения иерархии типов производный класс должен действительно быть подтипом базового класса. Само по себе желание переиспользовать код обычно не является достаточным основанием для построения такой иерархии.

Наследование корректно использовать для отношения \textbf{``является''} (\textit{is-a}):
\[
\text{Circle is a Shape}.
\]

Если же объект является лишь частью другого объекта, обычно следует использовать композицию:
\[
\text{Car has an Engine}.
\]

Наследование может быть:
\begin{itemize}
	\item одиночным --- класс имеет одного непосредственного предка;
	\item множественным --- класс имеет нескольких непосредственных предков;
	\item многоуровневым --- образуется цепочка наследования.
\end{itemize}

Множественное наследование может приводить к неоднозначностям. Классический пример --- \textbf{ромбовидное наследование}, когда два класса наследуют общий базовый класс, а затем некоторый четвёртый класс наследует оба из них. Различные языки решают эту проблему по-разному или вообще запрещают множественное наследование классов. Например Java запрещает множественное наследование классов, однако один класс может реализовывать несколько интерфейсов.

\subsection{Полиморфизм}

\textbf{Полиморфизм} --- возможность использовать один интерфейс для работы с объектами различных типов.

Идея полиморфизма состоит в том, что клиентский код задаёт объекту требуемую операцию, не обязательно зная его конкретный тип.

Например:
\begin{verbatim}
	for shape in shapes
	  print(shape.area())
	end
\end{verbatim}

В коллекции \texttt{shapes} могут одновременно находиться окружности, прямоугольники и другие фигуры. Для каждой из них вызывается одна операция \texttt{area}, однако выполняется соответствующая конкретному типу реализация.

Выделяют несколько видов полиморфизма.

\textbf{1. Полиморфизм подтипов.}

Объект производного типа может использоваться там, где ожидается объект базового типа:
\[
\texttt{Circle} <: \texttt{Shape}.
\]

Именно этот вид полиморфизма наиболее характерен для классического ООП.

\textbf{2. Параметрический полиморфизм.}

Алгоритм описывается независимо от конкретного типа данных. Примером являются шаблоны или обобщённые типы:
\begin{verbatim}
	List<T>
	Vector<T>
	max<T>(a, b)
\end{verbatim}

\textbf{3. Ad-hoc-полиморфизм.}

Одна операция имеет несколько реализаций для различных типов. Типичный механизм --- перегрузка функций или операторов.

Необходимо также различать:
\begin{itemize}
	\item \textbf{перегрузку} (\textit{overloading}): существуют разные функции с одинаковым именем, но различными наборами параметров.
	\item \textbf{переопределение} (\textit{overriding}): производный класс предоставляет новую реализацию метода, унаследованного от базового класса.
\end{itemize}

Полиморфизм подтипов часто реализуется посредством \textbf{динамического диспетчеризования}: конкретная реализация переопределённого метода выбирается во время выполнения программы в зависимости от фактического типа объекта, а не только от типа переменной, через которую к нему обращаются.

\subsection{Абстракция и интерфейсы}

\textbf{Абстракция} --- выделение существенных свойств объекта при игнорировании несущественных для решаемой задачи деталей.

Например, при использовании численного решателя пользователю может быть существенно, что он способен решать систему
\[
Ax=b,
\]

но не обязательно знать, реализован ли внутри метод Гаусса, $LU$-разложение или итерационный метод.

Абстракция позволяет работать на более высоком уровне:
\begin{verbatim}
	solver.solve(A, b)
\end{verbatim}

вместо непосредственного управления всеми деталями алгоритма.

Одним из основных средств задания абстракции является \textbf{интерфейс}.

Интерфейс определяет набор операций, которые объект обязан поддерживать, но не обязательно задаёт их конкретную реализацию.

Например:
\begin{verbatim}
	interface LinearSolver {
		solve(Matrix A, Vector b)
	}
\end{verbatim}

После этого могут существовать реализации:
\begin{verbatim}
	GaussianSolver
	LUSolver
	ConjugateGradientSolver
\end{verbatim}

Клиентскому коду достаточно работать с интерфейсом \texttt{LinearSolver}.

Это уменьшает связность компонентов программы:
\[
\text{клиент} \longrightarrow \text{абстракция},
\]

вместо
\[
\text{клиент} \longrightarrow
\text{конкретная реализация}.
\]

В некоторых языках существуют также \textbf{абстрактные классы}. Нельзя непосредственно создать объект абстрактного класса. Класс может содержать состояние, реализованные методы и абстрактные методы, реализация которых возлагается на производные классы.

Абстракция и инкапсуляция связаны, но обозначают разные идеи:
\begin{itemize}
	\item абстракция отвечает на вопрос \textit{``что умеет объект?''};
	\item инкапсуляция --- \textit{``что пользователь объекта не должен знать о его внутреннем устройстве?''}.
\end{itemize}

\subsection{Композиция и агрегация}

При построении сложных объектов широко используется отношение \textbf{``имеет''} (\textit{has-a}).

\textbf{Композиция} --- отношение между объектами, при котором один объект содержит другие объекты как свои составные части и управляет их жизненным циклом.

Например:
\begin{verbatim}
	class Car {
		Engine engine
	}
\end{verbatim}

Двигатель является составной частью автомобиля.

При строгой композиции время жизни составной части связано с временем жизни целого: уничтожение целого приводит к уничтожению его частей.

\textbf{Агрегация} --- более слабая форма отношения ``часть--целое''. Объект использует другой объект, но не обязательно владеет им и не управляет его жизненным циклом.

Например, кафедра содержит преподавателей, однако преподаватель как объект может существовать независимо от конкретной кафедры.

Условно:
\[
\text{композиция}
\quad\Rightarrow\quad
\text{сильное владение},
\]
\[
\text{агрегация}
\quad\Rightarrow\quad
\text{слабая связь}.
\]

Композиция часто является более гибкой альтернативой наследованию.

Пусть требуется изменить поведение объекта. При наследовании это поведение жёстко фиксируется иерархией типов:
\[
A \leftarrow B \leftarrow C.
\]

При композиции объект может делегировать работу другому объекту:
\[
A \longrightarrow B.
\]

Такой компонент можно заменить независимо от класса владельца.

Отсюда происходит известный принцип:
\begin{center}
	\textbf{предпочитать композицию наследованию, если наследование не выражает естественного отношения подтипов.}
\end{center}

\subsection{Принципы проектирования объектно-ориентированных систем}

Само использование классов и наследования не гарантирует хорошую архитектуру. При проектировании ООП-систем важно стремиться к:
\begin{itemize}
	\item высокой связности элементов внутри одного класса;
	\item слабой зависимости между различными классами;
	\item ясному распределению ответственности;
	\item минимизации знания одного компонента о внутреннем устройстве другого.
\end{itemize}

Одним из наиболее известных наборов рекомендаций являются \textbf{принципы SOLID}.

\textbf{S --- Single Responsibility Principle.}

Класс должен иметь одну основную ответственность и одну основную причину для изменения.

Например, класс численного решателя не должен одновременно решать систему, сохранять результаты в базу данных и строить графики.

\textbf{O --- Open/Closed Principle.}

Программные сущности должны быть открыты для расширения, но закрыты для модификации.

Желательно иметь возможность добавить новую реализацию алгоритма, не переписывая существующий клиентский код.

\textbf{L --- Liskov Substitution Principle.}

Объекты производного типа должны быть корректно взаимозаменяемы с объектами базового типа.

Если
\[
B <: A,
\]

то программа, корректно работающая с объектом типа $A$, должна сохранять корректность при подстановке объекта типа $B$.

Нарушение этого принципа означает, что иерархия наследования выбрана неправильно.

\textbf{I --- Interface Segregation Principle.}

Лучше использовать несколько небольших специализированных интерфейсов, чем один большой интерфейс, заставляющий класс реализовывать ненужные методы.

Например, вместо:
\begin{verbatim}
	interface NumericalObject {
		solve()
		draw()
		save()
		print()
	}
\end{verbatim}

целесообразнее определить независимые интерфейсы:
\begin{verbatim}
	Solvable
	Drawable
	Serializable
\end{verbatim}

\textbf{D --- Dependency Inversion Principle.}

Высокоуровневые компоненты не должны непосредственно зависеть от конкретных низкоуровневых реализаций. И те, и другие должны зависеть от абстракций.

Например, алгоритм вычислительного эксперимента должен зависеть от интерфейса
\begin{verbatim}
	LinearSolver
\end{verbatim}

а не непосредственно от класса
\begin{verbatim}
	GaussianEliminationSolver.
\end{verbatim}

Тогда конкретный решатель можно заменить без изменения логики всего приложения.

С SOLID тесно связан принцип \textbf{разделения ответственности} (\textit{separation of concerns}): различные аспекты программы должны по возможности быть изолированы друг от друга.

Также полезен принцип минимальной информированности: объект должен знать как можно меньше о внутренней структуре других объектов. Это уменьшает связность программных компонентов.

\subsection{Преимущества и ограничения объектно-ориентированного подхода}

К основным преимуществам ООП относятся:
\begin{itemize}
	\item \textbf{модульность} --- программа разделяется на относительно самостоятельные компоненты;
	\item \textbf{инкапсуляция состояния} --- локализуются изменения данных;
	\item \textbf{расширяемость} --- новые реализации могут добавляться через существующие абстракции;
	\item \textbf{повторное использование кода};
	\item \textbf{полиморфизм} --- единый код способен работать с объектами разных типов;
	\item \textbf{соответствие предметной области} --- многие системы удобно представлять как взаимодействие сущностей;
	\item \textbf{удобство сопровождения} при корректно спроектированной архитектуре.
\end{itemize}

Однако ООП не является универсальным решением.

К ограничениям относятся:
\begin{itemize}
	\item \textbf{усложнение} архитектуры при чрезмерном количестве классов и уровней абстракции;
	\item жёсткие иерархии наследования \textbf{могут затруднять} дальнейшее развитие системы;
	\item объектное представление \textbf{иногда хуже} соответствует задачам обработки больших однородных массивов данных;
	\item многочисленные мелкие объекты \textbf{могут ухудшать} локальность данных в памяти;
	\item чрезмерное применение шаблонов проектирования может приводить к \textbf{неоправданному усложнению} программы.
\end{itemize}

Особенно это заметно в высокопроизводительных и численных вычислениях. Например, представление миллиона частиц как миллиона сложных объектов может оказаться менее эффективным, чем хранение координат, скоростей и масс в отдельных непрерывных массивах.

Поэтому в современных программах ООП часто сочетается с другими парадигмами: процедурным, функциональным, обобщённым и data-oriented программированием.

Таким образом, центральная идея ООП состоит не в самом наличии классов, а в организации программы как системы взаимодействующих компонентов с чётко заданными ответственностями и интерфейсами.
